Case Study

Amazon Connect ↔ Microsoft Dynamics 365 Call Logging Integration

A scheduled AWS Lambda integration built for Paintback that turns every Amazon Connect contact-centre call (inbound, outbound, or voicemail) into a Microsoft Dynamics 365 Phone Call activity automatically, matched to the caller's CRM contact record via the Dynamics Web API, with no agent ever touching Dynamics by hand.

  • Microsoft Dynamics 365
  • Dynamics Web API v9.2
  • OAuth2
  • Java 17
  • AWS Lambda
  • Amazon Connect
  • Docker
  • Amazon EventBridge
  • Amazon DynamoDB
  • Amazon S3
  • CloudFormation
  • Bitbucket Pipelines

◆ The Problem

Paintback's customer service team takes calls through Amazon Connect, but every customer record, case, and history the team actually works from lives in Microsoft Dynamics 365. Amazon Connect has no native connector into Dynamics, so without this integration a call happens, gets logged in Connect's own contact trace records, and then simply isn't visible anywhere a Dynamics user would look: no phone call activity on the customer's timeline, no record an agent called back, no way to see call history alongside cases and correspondence.

The integration closes that gap by treating Dynamics 365 as the system of record for customer communication: on a 5-minute schedule, it pulls whatever calls finished in Amazon Connect since the last run, works out who the caller actually was in Dynamics, and writes a properly-typed Phone Call activity back (incoming, outgoing, or voicemail) linked to that contact.

◆ How It Works

One Lambda invocation, fired by EventBridge every five minutes, authenticates to Dynamics once and reuses that token across every call it processes in that run; individual calls are then fanned out to a 100-thread pool so a busy 5-minute window doesn't serialise against the Dynamics API.

1

Authenticate to Dynamics 365

The handler opens every run with an OAuth2 Resource Owner Password Credentials request against Microsoft's login.microsoftonline.com token endpoint, using a dedicated Dynamics API user. The resulting bearer token is reused for every contact and every subsequent Dynamics Web API call made during the invocation.

2

Find New Calls in Amazon Connect

SearchContacts is called against the Amazon Connect instance for anything whose DISCONNECT_TIMESTAMP falls between the last recorded run time (bookmarked as JSON on S3) and now; the new bookmark is only written once the batch is fetched successfully.

3

De-duplicate via DynamoDB

Every contact id is checked against a DynamoDB idempotency table before any Dynamics call is made: already-succeeded contacts are skipped, permanently-failed ones (>3 retries) are ignored, and new or retryable ones are queued to the thread pool as a ContactIdProcessor task.

4

Enrich & Classify the Call

Per contact, DescribeContact and GetContactAttributes pull the channel, initiation method, timestamps, and the customer's phone number, which is used to compute call duration and to classify the interaction as an incoming call, outgoing call, or voicemail.

5

Resolve the Dynamics Contact

The caller's number is matched against every phone field on the Dynamics contacts entity (mobile, telephone 1–3, and assistant phone), comparing the last 8 digits only, so formatting differences (country codes, spacing, leading zeros) between Connect and Dynamics don't break the match.

6

Write the Phone Call Activity

A phonecalls record is POSTed to the Dynamics Web API with subject, description, direction, actual start/end, duration in minutes, and, when a match was found, the contact bound via an @odata.bind-style reference, so the call appears directly on that customer's timeline.

7

Record & Self-Heal

Success or failure is written back to DynamoDB and reported to Symphony3's central integration-notifier webhook. A final FailedContactProcessor pass re-drives any contact still received/failed for more than 3 minutes, capped at 3 retries, so a transient Dynamics outage self-heals on the next few runs instead of losing the call.

There's no persistent server and no public endpoint in production: the container image Lambda sits inside Paintback's VPC on a private subnet and is invoked directly by the EventBridge schedule rule, not exposed over HTTP. A local template.yaml (AWS SAM) adds a POST /call API Gateway route purely so the same handler can be triggered on demand during development.

Dynamics 365 is treated as the source of truth for who the caller is: Amazon Connect only ever supplies a phone number and call metadata, while every write (the Phone Call activity itself, and the contact it's linked to) goes through the Dynamics Web API (/api/data/v9.2/), authenticated per-invocation rather than with a long-lived cached token.

◆ Dynamics 365 Call Classification

Amazon Connect's channel and initiation-method fields are mapped onto Dynamics 365's Phone Call option-set values so every activity shows the right direction and icon in the CRM, not just a generic logged call:

Amazon ConnectDynamics 365 Phone CallDirection Code
Channel VOICE, method INBOUNDIncoming call (100000000)directioncode = false
Channel VOICE, method OUTBOUNDOutgoing call (100000001)directioncode = true
Channel TASK (voicemail)Voice mail (100000002)directioncode = false

newtype and directioncode are custom/standard Phone Call fields on the Paintback Dynamics org used to drive this classification; the subject line itself is generated per type (e.g. "Call from {number} to call centre" vs "Voicemail from {number} to call centre") so agents can scan the timeline without opening every activity.

◆ Data & Persistence

Dynamics 365 itself holds no integration state; it only ever receives finished Phone Call activities. Everything the Lambda needs to know what's already been processed lives outside it, in S3 and DynamoDB.

S3 bucket layout 
TenantConfigurations/
└─ {TENANT_ID}/
    └─ last_run_time/
        └─ last_runtime.json      # ISO timestamp of the last successful SearchContacts window

DynamoDB's integrationrecords table (partitioned by tenant_integrations_id, sorted by source_id = the Connect contact id) is the only durable idempotency record: it tracks current_status (received → success/failed), retry_count, and the resulting Dynamics target_id (the phone call's activityid), so a call that already reached Dynamics is never logged twice even if the same 5-minute window is scanned again.

mvn clean package (Maven Shade) builds a fat jar around the AWS Lambda Java Runtime Interface Client; the Dockerfile packages it as a container image. cloudformations/cloudformation.yml provisions the image-based Lambda inside Paintback's VPC on a private subnet with its own security group, an execution role scoped to the tenant's S3 config prefix plus DynamoDB and ENI permissions, and an EventBridge rule on a cron(0/5 * * * ? *) schedule, with separate CloudFormation stacks and separate Dynamics 365 environments (UAT vs production org) for develop and production. A dedicated run-sonar-scan-quality-gw pipeline runs SonarCloud analysis ahead of every merge.

Unit tests (JUnit 5 + Mockito) cover the handler, managers, models, operators, and processors, with JaCoCo wired into the Maven build to produce coverage reports on every verify.

◆ Good to Know

  • Runs entirely inside Paintback's VPC on a private subnet with no public HTTP endpoint in production: EventBridge invokes the Lambda directly every 5 minutes, and the SAM template's POST /call route exists only for local development.
  • Dynamics 365 authentication uses the OAuth2 Resource Owner Password Credentials grant against a dedicated service account, re-authenticated once per invocation rather than caching a long-lived token across runs.
  • Contact matching compares only the last 8 digits of a phone number across five Dynamics contact fields, which was a deliberate trade-off to tolerate inconsistent country-code and spacing formats between Connect and Dynamics.
  • Up to 100 calls are processed concurrently per run via a fixed thread pool; DynamoDB caps retries at 3 attempts with a 3-minute cool-down before a received/failed record is retried.
  • Separate dev and production stacks point at entirely separate Dynamics 365 organisations (UAT vs production CRM), not just separate environment variables on the same org.
