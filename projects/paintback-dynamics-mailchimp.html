Case Study

Microsoft Dynamics 365 ↔ Mailchimp Marketing List Sync

A daily AWS Lambda integration built for Paintback that keeps every Mailchimp audience in lock-step with its matching Microsoft Dynamics 365 marketing list, treating Dynamics as the single source of truth and reconciling each list's Mailchimp membership against it: new contacts created, changed contacts updated, and removed contacts unsubscribed, automatically.

  • Microsoft Dynamics 365
  • Dynamics Web API v9.2
  • OAuth2
  • Mailchimp API v3
  • Java 17
  • AWS Lambda
  • Docker
  • Amazon EventBridge
  • CloudFormation
  • Bitbucket Pipelines
  • SonarCloud

◆ The Problem

Paintback manages its customers, prospects, and segmentation entirely inside Microsoft Dynamics 365 as marketing lists, but the actual email campaigns go out through Mailchimp, which has no visibility into Dynamics at all. Left alone, the two drift apart immediately: someone gets added to a Dynamics marketing list and never receives a single campaign; someone unsubscribes or is removed in Dynamics and keeps getting emailed anyway; a contact updates their name or phone number in the CRM and Mailchimp silently goes stale.

Rather than trying to catch every change in Dynamics as it happens, this integration takes the simpler, more reliable route: once a day, for every active marketing list, it asks "who is in this list in Dynamics right now?", compares that against "who is actually a Mailchimp subscriber for the matching audience right now?", and reconciles the difference: no separate state store, no drift that can silently compound over time.

◆ How It Works

One Lambda invocation, fired by EventBridge once a day, authenticates to Dynamics once and reuses that token for every list; the lists themselves are processed concurrently, and within each list every create/update/delete is fanned out across its own 100-thread pool.

1

Authenticate & Discover

The handler authenticates to Dynamics via OAuth2 (Resource Owner Password Credentials), fetches every active marketing list (statecode eq 0) from /api/data/v9.2/lists, and fetches every Mailchimp audience the account has, paginating both in batches of 1000.

2

Match List to Audience

For each Dynamics marketing list, DynamicsToMailchimpProcessor looks for a Mailchimp audience with the exact same name. No match, no sync: the list is skipped rather than guessed at, so onboarding a new list is just naming the Mailchimp audience to match.

3

Fetch Both Sides

listmembers gives the set of Dynamics contact ids currently on the list; those ids are then batched into an OData contactid eq … or … filter against /contacts to pull name, phone, and email in one query. In parallel, every existing member of the matching Mailchimp audience is fetched via the Mailchimp API.

4

Diff by Email

Both sides are reduced to a set keyed by email address. Anyone in Dynamics but not Mailchimp is queued to create; anyone in both whose name or phone differs is queued to update; anyone in Mailchimp but no longer in the Dynamics list is queued to delete.

5

Reconcile Mailchimp

ContactProcessor executes each action: create POSTs a new subscribed member with merge fields for first name, last name, and phone; delete removes a member by the MD5 hash of their lower-cased email (Mailchimp's addressing scheme); update is implemented as a delete immediately followed by a create, keeping the write path to a single well-tested code path instead of a separate PATCH flow.

6

Report

Every create/update/delete outcome, success or failure, fires an IntegrationCompletedEvent to Symphony3's central integration-notifier webhook, with the contact's email masked before it's logged or reported.

There's no database in this integration: no DynamoDB idempotency table, no S3 bookmark. Because every run recomputes the full desired state (Dynamics list membership) against the full actual state (Mailchimp audience membership) and only acts on the difference, re-running the same day twice is safe: anything already reconciled simply produces an empty diff.

Dynamics 365 is authoritative for who should be on the list and what their details are; Mailchimp is treated purely as a delivery mechanism that gets brought into agreement with it, never the other way around: a change made directly in Mailchimp is overwritten on the next run rather than flowing back to Dynamics.

◆ Reconciliation Logic

Once both sides of a list are reduced to an email → contact map, three independent passes decide what happens to each address:

ConditionActionMailchimp Call
Email in Dynamics list, not in Mailchimp audienceCreatePOST /lists/{id}/members (status subscribed)
Email in both, but name or phone differsUpdateDELETE the existing member by email-hash, then re-POST
Email in Mailchimp audience, no longer in Dynamics listDeleteDELETE /lists/{id}/members/{md5(email)}
Email in both, all fields identicalNo-opn/a

A contact's email is resolved as email1, falling back to email2 if the primary is blank; phone is resolved from mobile → telephone1 → telephone2 → telephone3, first non-empty value wins. Member identity on the Mailchimp side is always the MD5 hash of the lower-cased email address, per Mailchimp's own addressing scheme for the members endpoint.

◆ Design Pattern: Event Reporting

Every outcome (a Dynamics fetch failing, a Mailchimp create/update/delete succeeding or failing) is reported the same way, through a small factory/strategy pair rather than instantiating the event manager directly wherever it's needed:

event reporting 
EventTaskFactory (interface)
└─ IntegrationCompletedEventTaskFactory
    └─ create(data, trackId) -> new IntegrationCompletedEventManager(data, trackId)

EventManager(taskFactory)
└─ handleEvent(data, trackId)
    └─ runs taskFactory.create(...) on a single-thread executor and blocks for it to finish

The indirection means every call site (token failures, list-fetch failures, contact create/update/delete outcomes) goes through new EventManager(new IntegrationCompletedEventTaskFactory()).handleEvent(...) rather than duplicating thread-management code, and a second event type (say, a different webhook for a different tenant) would only mean adding a new factory.

◆ Good to Know

  • Stateless by design: no DynamoDB idempotency table and no S3 bookmark; every run recomputes the full diff between Dynamics and Mailchimp, so a re-run or a missed day is self-correcting rather than something that needs manual recovery.
  • Dynamics 365 is always the winning side: a change made directly in a Mailchimp audience (a manual unsubscribe, an edited merge field) is overwritten on the next daily run rather than syncing back into Dynamics.
  • A Dynamics marketing list only syncs if a Mailchimp audience with the exact same name already exists: lists are matched by name, not by a stored id mapping.
  • "Update" is implemented as delete-then-create rather than a Mailchimp PATCH, trading one extra API call for a single, uniformly-tested write path shared with create.
  • Runs entirely inside Paintback's VPC on a private subnet with no public HTTP endpoint in production: EventBridge invokes the Lambda directly once a day, and the SAM template's POST /marketingList route exists only for local development.
  • Every contact's email is masked before it's logged or sent to the completed-event webhook, so raw addresses don't end up in logs or monitoring payloads.
