Case Study

Civica Authority ↔ OneBlink Job & Prefill Integration

A scheduled AWS Lambda that turns a new Civica Authority workflow task into a ready-to-complete OneBlink field job: it enriches the task from eight related Authority records, JOLT-transforms the result twice, and dispatches a pre-filled inspection form so an officer in the field opens a job that already knows the applicant, the property, and the work being assessed.

  • Civica Authority

◆ About OneBlink

OneBlink is an Australian govtech platform local councils use to build digital forms and dispatch them to field staff as mobile Jobs, complete with offline capture and PDF generation, so an inspecting or assessing officer can fill in a form from a phone or tablet on-site rather than on paper. Councils commonly pair it with their core regulatory system, in this case Civica Authority, so a dispatched job doesn't start as a blank form: the applicant, the property, and the nature of the work are already on the page before the officer even opens it.

◆ The Problem

When an Authority workflow task reaches an inspection or assessment stage, someone has to hand that work to a OneBlink job for the officer who'll actually go out and look at it. Built by hand, that means an officer (or an administrator on their behalf) re-typing the applicant's name, the property address, the parcel details, the type of work proposed, and any existing task notes into a OneBlink form, all of which Authority already knows, before the actual inspection can even start. Every manual re-entry is also a chance to introduce a typo that then shows up on the officer's PDF report.

This integration removes that step entirely: five minutes after a qualifying task appears in Authority, the matching OneBlink job already exists, pre-filled, waiting for an officer to open it.

◆ How It Works

1

Discover Qualifying Tasks

JobService pages through Authority workflow tasks modified since the last run (an S3 bookmark, Melbourne local time), filtered server-side by every configured (document type, workflow action code) pair, then keeps only tasks that are genuinely newly-actionable, no determination code yet, inside the trigger window, and matching a configured task type, rather than every task the filter happens to return.

2

Check for an Existing Job

JobAsyncProcessor looks up any OneBlink job already tagged with this task's external id (formattedAccount/taskId). If one exists, it's deleted rather than left alone, so a retried or re-triggered task always ends up with exactly one current job, never a stale duplicate sitting next to a fresh one.

3

Enrich from Authority

A chain of Authority calls builds up one SourcePayload: the actioning officer's name, the application record, its linked property, the parcel address and property/parcel record, the proposal type (resolved through a separate building/development type lookup), the task's own comment thread, and a computed description of works.

4

Transform Twice

The enriched payload runs through two separate, independently cached JOLT specs, one producing the OneBlink prefill data, the other producing the OneBlink job request itself, so the two OneBlink API shapes can evolve independently of each other and of Authority's own data model.

5

Prefill, Then Create the Job

The prefill payload is PUT to OneBlink against the form mapped to this task type; OneBlink hands back a preFillFormDataId tucked inside a response header, which is then attached to the job payload before it's POSTed to create the actual job.

6

Record & Report

The new job's id is written to DynamoDB against the task's source id, and an IntegrationCompletedEvent fires to the platform's completed-event endpoint whether the run succeeded or failed. A separate retry pass re-drives any DynamoDB entry still failed/received after a 3-minute cool-down.

Discovery runs once per invocation; every task that passes the filter is then handed to its own async task on a dedicated Spring thread pool (@Async("ThreadExecutor")), so a busy 5-minute window processes tasks concurrently rather than one at a time, mirroring the same async fan-out pattern used across this developer's other Civica Authority integrations.

◆ Authenticating to OneBlink

OneBlink's developer-key authentication issues a signed JWT built from an access key and a secret key, and its official SDKs are JavaScript/.NET only. With no Java SDK available, OneBlinkHelper builds the token by hand: an HS256 header and a payload carrying iss, iat, and exp (plus optional sub/oneblink:access claims the app doesn't currently use), signed with HmacSHA256 and base64url-encoded, deliberately mirroring the claim shape OneBlink's own .NET SDK produces so the token is accepted the same way.

JWT construction (app/helpers/OneBlinkHelper.java) 
header  = base64url({"alg":"HS256","typ":"JWT"})
payload = base64url({"iss": accessKey, "iat": now, "exp": now + 3600})
signature = base64url( HmacSHA256(header + "." + payload, secretKey) )
token = header + "." + payload + "." + signature

The token is short-lived (one hour) and regenerated at the start of every Lambda invocation rather than cached across warm containers, keeping the token logic stateless and simple at the cost of one extra signing operation per run.

◆ The Authority Enrichment Chain

One qualifying task drives a fixed sequence of further Authority lookups before it's ready to transform, each one optional and skipped cleanly if its source field is missing:

StepAuthority CallAdds
1Name by idActioning officer's name
2Document by formatted accountThe application/document record
3Document → property linkLinked property/parcel id
4Parcel address by idStreet address for the property
5Property parcel by idFull parcel/lot record
6Application proposals → proposal typeBuilding or development work type
7Task comment by task idMost recent comment on the task
8Document descriptionDescription of works, appended with the proposal type description for certain document types

Everything lands on one SourcePayload object, which is what both JOLT specs actually transform, so adding a new field to a prefill or job mapping is a config change to a spec file, not a Java change, as long as the underlying data is already on the payload.

◆ Good to Know

  • An existing OneBlink job for the same task is always deleted and recreated rather than left alone, so a retried task, or the same 5-minute window catching a task twice, never results in duplicate jobs sitting in an officer's queue.
  • The prefill id doesn't come back in OneBlink's response body: it's tucked inside an x-oneblink-response header as a small JSON blob, which OneBlinkHelper parses out separately from the main response handling.
  • No official Java SDK exists for OneBlink's developer-key auth, so the signed JWT is generated by hand, deliberately matching the claim shape OneBlink's own .NET SDK produces rather than inventing a new one.
  • A task only qualifies once its modified timestamp has genuinely diverged from its created timestamp and it carries no determination code yet, a business rule change requested after the integration first went live, not the original design.
  • The retry pass re-fetches the task from Authority before reprocessing it and compares modified timestamps, so a task that's moved on since it failed is caught rather than silently reprocessed against stale data.
  • Only a UAT deployment pipeline exists today; a Prod pipeline is called out in the project's own documentation as not yet set up.
