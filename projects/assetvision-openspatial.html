Case Study

AssetVision ↔ OpenSpatial Asset Sync API

A serverless Spring Boot integration that keeps Civica AssetVision (enterprise asset & financial register) and Munsys OpenSpatial (field GIS/spatial system) in sync bidirectionally — and does it for many councils at once by keeping every field mapping in a swappable JOLT spec instead of Java code.

  • Java 17
  • Spring Boot 3.5
  • AWS Lambda
  • aws-serverless-java-container
  • JOLT / Chainr
  • Multi-Tenant
  • Application Load Balancer
  • Amazon S3
  • Bitbucket Pipelines
  • Swagger / OpenAPI

◆ The Problem

A council's asset data usually lives in two systems that don't agree on anything except the asset itself: AssetVision, the enterprise asset and financial register, and Munsys OpenSpatial, the GIS system field crews use to capture pipes, valves, hydrants, and manholes on a map. When a crew creates or edits an asset spatially, AssetVision needs to know. When AssetVision's asset lifecycle changes, OpenSpatial's record needs to follow. That's a bidirectional sync problem on its own — but the harder part is that no two councils configure their OpenSpatial tables or their AssetVision attribute schema the same way.

Hand-writing a mapping in Java for one council's field names and reference lists doesn't transfer to the next council without a code change and a redeploy. This project's core design decision was to push that entire mapping — which source field goes to which target attribute, using which reference list, for which asset type — out of the codebase and into a declarative, swappable JOLT specification, so one Lambda function serves every tenant.

◆ How It Works

1

Spatial → AssetVision

Munsys posts an asset change to PUT /spatials/spatial, tagged with an operation of INS, UPD, or DEL. The x-api-key header resolves the request to a tenant before anything else happens.

2

JOLT Transform

The tenant's own JOLT spec is loaded from cloud storage and run through Chainr to reshape the raw OpenSpatial attributes into an AVAssetCreateReq AssetVision understands — no per-council code path involved.

3

AssetVision API Call

Depending on the operation, the service creates, patches, or soft-deletes the matching AssetVision asset — looking it up by its OpenSpatial GID when it needs to update or delete an asset it didn't just create.

4

AssetVision → Spatial

The reverse path runs the same way: AssetVision posts to POST/PUT /assets/asset, and a network-trace event lands on POST /spatials/trace to attach a completed trace back onto an AssetVision job by ID.

5

Audit Trail

Every request — success or failure, in either direction — posts a completed-event notification to a central audit endpoint, the same pattern used across this developer's other Civica integrations.

◆ The JOLT Transformation Framework

This is the part that makes the integration reusable rather than a one-off. JOLT is a declarative JSON-to-JSON transformation library: instead of writing Java code that reads field A and writes field B, you write a JSON spec that says so, and a Chainr pipeline executes it. The project wraps that engine in a single reusable component:

JoltHelper.java 
public Object transform(String inputJsonString, List<Object> joltSpec) {
    Map<String, Object> inputJSON = mapper.readValue(inputJsonString, Map.class);
    Chainr chainr = Chainr.fromSpec(joltSpec);
    return chainr.transform(inputJSON);
}

public <T> T transformToClass(String inputJsonString, List<Object> joltSpec, Class<T> clazz) { ... }
public <T> T transformPojoToPojo(Object sourcePojo, List<Object> joltSpec, Class<T> targetClass) { ... }
public String transformJsonToJson(String inputJsonString, List<Object> joltSpec) { ... }

Crucially, the spec itself isn't bundled in the jar. AVHelper pulls it per request via configManager.getOsToAVSpec(intData), which resolves to that tenant's own JSON file in cloud storage. Onboarding a new council is a config change — write and upload their spec — not a Java change and a redeploy. The same JoltHelper, AVManager, and SpatialManager serve every tenant; only the spec differs.

Reading the spec: four techniques doing the real work

1. Branching on the source's own node type. A single OpenSpatial table like SP_SEWNODE fans out into completely different AssetVision attribute sets depending on what kind of node it actually is — a manhole gets depth and lid-type fields, a valve gets material and setting fields — all from one shift block keyed on NODE_TYPE:

"@(2,NODE_TYPE)": {
  "LAMPHOLE|MANHOLE_PUB|RODDING_EYE": {
    "@(4,NODE_DEPTH)": "tmp.ManholeDepth.Value",
    "@(4,LID_TYPE_LVALUE)": "tmp.ManholeLidType.ReferenceListItems[0].Value",
    "#Sewer Access Point": ["AssetTypeName","Name"]
  },
  "AIR_VAC_RELEASE|SCOUR_VALVE|OPEN_VALVE": {
    "@(4,NODE_DEPTH)": "tmp.Depth.Value",
    "@(4,SETTING_LVALUE)": "tmp.ValveSetting.ReferenceListItems[0].Value",
    "#Valve": ["AssetTypeName","Name"],
    "#Sewer": "tmp.FacilityNetworkCategory.ReferenceListItems[0].Value"
  }
}

The pipe-delimited keys (LAMPHOLE|MANHOLE_PUB|RODDING_EYE) are JOLT's OR-match syntax, and the "#Sewer Access Point" literal writes that same constant string into both AssetTypeName and Name in one move — a static label becomes both the category and the display name.

2. Value/code pairs and one-to-many fan-out. Reference-list fields are always shifted in pairs from the same lookup, and some values are written to more than one target at once:

"@(2,PIPE_MATRL_LVALUE)": "tmp.MaterialMulti.ReferenceListItems[0].Value",
"@(2,PIPE_MATRL_LCODE)":  "tmp.MaterialMulti.ReferenceListItems[0].Code",
"@(2,GEOM_LENGTH)": ["tmp.PipeLength.Value", "tmp.MeasureQuantity.Value"]

One source value, GEOM_LENGTH, simultaneously populates a domain-specific PipeLength attribute and a generic MeasureQuantity attribute that other asset types share — without reading the source twice.

3. A self-describing attribute schema. Later in the chain, a default operation doesn't fill in missing data — it attaches Name/DataType metadata to every one of ~80 possible fields, before a second shift flattens all of them into one generic array:

{ "operation": "default", "spec": { "tmp": {
    "AssetName": {"Name": "Asset Name", "DataType": "String"},
    "Depth":     {"Name": "Depth (mm)", "DataType": "Number"}
}}},
{ "operation": "shift", "spec": { "tmp": {
    "AssetName": "Attributes[]",
    "Depth":     "Attributes[]"
}}}

That's what lets AssetVision's API accept one uniform Attributes[] array instead of ~80 hardcoded fields — each entry already knows its own display name and data type.

4. Normalising types at the edge. Since those ~80 fields started life as strings, numbers, dates, and reference lists, a final modify-overwrite-beta step coerces every attribute's value to a string using JOLT's built-in function support, so AssetVision always receives the same shape regardless of source type:

{ "operation": "modify-overwrite-beta", "spec": { "Attributes": { "*": {
    "Value": "=toString(@(1,Value))"
}}}}

Combined with a modify-default-beta step that guarantees fields like AssetStatus always resolve to an Active reference item even when the source omitted one, the whole pipeline — branch, map, describe, flatten, normalise, default — runs as a single Chainr call per request, entirely swappable per tenant.

Both directions share the same shape: a controller validates the tenant's x-api-key, a service resolves the operation, JoltHelper reshapes the payload through that tenant's spec, and a manager class owns authentication and the outbound call — AVManager caches an OAuth2 password-grant token for AssetVision, SpatialManager caches an API-key token for OpenSpatial and reads its expiry straight out of the JWT. A ConfigManager sits underneath both, caching each tenant's config and tokens for 30 minutes so most requests don't re-fetch from storage or re-authenticate at all.

Rather than the more typical API Gateway front door, this Lambda sits behind the same kind of shared Application Load Balancer used elsewhere in this developer's projects — the ALB's listener rule forwards matching hostname/path traffic straight to the function, with multi-value headers enabled so the aws-serverless-java-container bridge can translate the ALB event into a normal Spring MVC request. The Lambda runs container-image based (256–1024 MB configurable, 300s timeout) inside the VPC, with an execution role scoped to CloudWatch Logs, VPC networking, and S3 read/write for the tenant config and audit bucket. A second pipeline, createEcr-UAT, provisions the ECR repository a new environment needs before its first deploy.

Every endpoint requires an x-api-key header, validated per endpoint group (api.key.assets for /assets/*, api.key.spatials for /spatials/*), and interactive Swagger/OpenAPI docs are served at /swagger.html alongside the API.

◆ Good to Know

  • Tenant resolution, secrets, and the JOLT spec itself are all fetched from cloud storage per request and cached for 30 minutes — the first request after a cold start or cache expiry is the slowest.
  • Authentication inbound is a shared per-tenant API key rather than per-user identity; outbound calls to AssetVision use OAuth2, and to OpenSpatial a short-lived JWT whose expiry is read directly from the token.
  • Verified manually against UAT instances of both systems; no automated integration test suite yet.
  • A local Spring profile (-Plocal) runs the same code on embedded Tomcat for development, separate from the LambdaHandler entry point used in deployment.
