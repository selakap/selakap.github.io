Case Study

Authority NAR Contact Resolution API

A Spring Boot integration service that resolves a caller's phone number into Civica Authority contact records in real time, and aggregates a resident's CRM history, rates, and property/GIS records into a single 360° view — a proof-of-concept built for council contact-centre and customer-service teams.

◆ The Problem

When a resident calls a council contact centre, the only thing an operator usually has is a phone number. Turning that into a resident's identity and full history inside Civica Authority means manually searching the Name Register, then separately opening CRM enquiry history, rates and property records, and GIS documents — across several screens and logins. There's no single phone-first entry point into Authority's data, and no consistent audit trail proving a lookup happened and what it returned.

This proof-of-concept closes that gap with two purpose-built endpoints on top of Civica Authority's OData/REST APIs: a machine-readable phone-to-contact resolver for telephony/CTI systems, and a human-readable 360° dashboard that assembles a resident's CRM, rates, and property/GIS records onto one screen.

◆ How It Works

1

Phone Lookup

An external system (e.g. a CTI/telephony platform) calls GET /api/contact/search?phone={number}. The service authenticates against Civica Authority via an OAuth2 password grant, then queries the Name Register for any contact whose mobile phone matches.

2

Match Resolution

Matching Name Register (NAR) records are normalised into first name, last name, full name, address, and NAR ID, and returned as JSON so the calling system can present or auto-select the right contact.

3

360° View Request

Once a NAR ID is known, GET /contact/360view?nar={narId} fans out to three data pulls: paginated CRM enquiry history, rate-payer & parcel records, and Civica GIS document URLs for each parcel and assessment.

4

Dashboard Render

Results are pushed into a server-rendered Thymeleaf dashboard showing the resident's name, address, and NAR ID up top, with tabbed CRM and Rates tables below — each row deep-linking straight back into Authority's own CRM enquiry and GIS screens.

5

Audit Trail

Whether a lookup succeeds or fails, an async event service posts a signed integration-completed event — tenant, integration ID, status, response code — to a central audit endpoint, so every phone lookup and every 360° view is independently traceable.

Requests flow through four clean layers: controllers accept and validate the HTTP request, NarService orchestrates the use case, AuthorityHelper maps Authority's OData responses into the API's own domain model, and AuthorityManager owns every outbound call — token generation and all REST/OData requests — through a shared HttpHelper that centralises logging, timeouts, and error handling. Every request carries a short tracking ID that's threaded through every log line for end-to-end traceability.

Spring Security guards every route with HTTP Basic authentication except /healthz, which is left open for the load balancer's health checks.

The 360° view is the most involved flow: CRM history is paged through in batches of 100 until Authority stops returning full pages, each rate-payer record is resolved down to its parcel, and each parcel triggers two more calls — a GIS integration request followed by a signed URL lookup — to produce direct links to the parcel map and the assessment map. All of it is assembled and rendered before the dashboard is returned.

A custom deployNarApi-UAT Bitbucket pipeline builds the Spring Boot app with a multi-stage Maven → Alpine-JRE Dockerfile, tags the image with a build timestamp, pushes it to Amazon ECR, and runs aws cloudformation deploy against a template that provisions (or updates) an ECS Fargate service — 256 CPU units, 512 MB memory, one task, no public IP — sitting behind an existing shared Application Load Balancer. A listener rule routes /contact/* and /api/contact/* to the service's target group, with health checks every 30 seconds (2 healthy / 3 unhealthy thresholds) and a CloudWatch log group retaining logs for 90 days.

Authority credentials, OAuth2 client details, and the audit endpoint URL are injected purely as CloudFormation parameters at deploy time — nothing is hardcoded in the image or the repo.

◆ Good to Know

As a proof-of-concept rather than a finished product, a few things are intentionally out of scope for now:

  • Authentication is a single shared HTTP Basic credential — there's no per-operator identity or role-based access yet.
  • Built for a single Civica Authority tenant; multi-tenant routing isn't implemented.
  • No caching layer — every phone search and 360° view re-queries Authority live, including the OAuth2 token exchange.
  • Verified manually against a UAT Authority instance; no automated integration test suite yet.
