Case Study

Civica Authority ↔ Assetic Work Requests & Work Orders Integration

A serverless AWS Lambda integration that keeps Civica Authority (CRM / customer request management) and Assetic (asset & works management) in sync for a council or utility tenant: new CRM tasks automatically become Assetic Work Requests, and Work Request/Work Order lifecycle events in Assetic flow back as CRM task updates, with DynamoDB-backed idempotency and automatic retries on every 5-minute run.

◆ The Problem

A council's field operations usually run on two systems that don't talk to each other: Civica Authority, where a resident's request becomes a CRM task, and Assetic, where the actual inspection or repair is scheduled and tracked as a Work Request or Work Order. Someone has to notice a new investigation task, manually raise the matching Work Request, then chase Assetic for status (inspector assigned, rejected, completed) and manually reflect that back onto the CRM task so the resident's request shows accurate progress.

Neither system exposes a webhook the other can lean on, so this integration runs as a scheduled poller instead of an event listener: every five minutes it checks both systems for anything new since the last run, in both directions, and reconciles the difference, while making sure a transient failure on either side never means the request has to start over.

◆ How It Works

A single Lambda invocation, fired by EventBridge every five minutes, runs four stages sequentially, each stage finishes before the next starts, but the items inside a stage are farmed out to a 100-thread pool and processed concurrently.

1

Authority → Assetic

AuthorityTasksProcessor polls Authority for CRM tasks created since the last run, matches each one's category and action code against the tenant's configured mapping, then dispatches it: an ACTN (investigate) task creates a brand-new Assetic Work Request and uploads its Authority attachments; a CRF* (further information) task appends its notes as supporting information onto the existing Work Request.

2

Assetic → Authority: Work Requests

AsseticMainWRsProcessor polls Work Requests modified since the last run, keeps only the ones whose ExternalIdentifier matches the Authority account pattern, and independently checks three conditions per Work Request (inspector assigned, status rejected/cancelled, new supporting info), opening or closing the matching ASS* Authority task for whichever apply.

3

Assetic → Authority: Work Orders

AsseticMainWOsProcessor polls Work Orders modified since the last run and evaluates four conditions per order (created, in-progress, completed, new supporting info), opening the "works approved" and "assigned to a team" tasks, closing the original investigate task on completion, and adding notes for anything else.

4

Retry

RetrierProcessor runs last: it re-uploads attachments for recently-succeeded Work Requests in case the original upload failed, then scans DynamoDB for entries stuck in received/failed* for more than 3 minutes with fewer than 4 retries, and re-dispatches each back through the processor matching its source id; anything still failing after 4 attempts is left for manual investigation.

There's no persistent server component: EventBridge fires the container-image Lambda, it authenticates against Authority once per invocation and reuses that token across all four stages, and everything each stage needs to decide what's "new" (per-tenant category/action-code mappings and per-poll bookmarks) is read from S3 rather than hardcoded, so the same image serves every tenant.

DynamoDB (integrationrecords) is the only durable state: every processed item gets a row keyed by direction (tenant_integrations_id) and source id, recording status, retry count, and the downstream id it produced, so an already-succeeded item is never reprocessed, and a failed one resumes instead of duplicating work.

◆ Task/Status Code Reference

Every direction is driven off Authority's own workflow action codes, mapped in TenantConstants:

CodeMeaning
ACTNNew investigation task → creates an Assetic Work Request
CRFFurther-information task → adds Work Request supporting info
ASS1Opened when a Work Request is rejected/cancelled in Assetic
ASS2Opened when an inspector is assigned in Assetic
ASS3Opened when a Work Order is created in Assetic
ASS4Opened when a Work Order moves in-progress
ASS5Opened for new Work Request supporting info
CAC / CCOMDetermination codes used to close ASS* and ACTN tasks respectively

DynamoDB's current_status moves through received → success | failed | failed_actn (a task-notes-specific failure), which is what the retry stage scans for.

◆ Data & Persistence

The S3 bucket holds everything that varies per tenant: which CRM categories should raise a Work Request, and where each polling loop last left off.

S3 bucket layout 
TenantConfigurations/
└─ {TENANT_ID}/
    ├─ AuthorityTaskConfig/
    │   └─ config.json              # category_id + action_code[] -> raise a WR?
    └─ last_run_time/
        ├─ last_runtime_authority.json
        ├─ last_runtime_assetic_work_request.json
        └─ last_runtime_assetic_work_order.json

DynamoDB's integrationrecords table is purely for idempotency and retry bookkeeping, one row per processed item, partitioned by direction (tenant_integrations_id) and sorted by source_id, which encodes enough context to route a retry back to the right processor (e.g. wrInspect{account}, woNew{account}). Every terminal outcome, success or failure, also fires an IntegrationCompletedEvent to an external webhook so status is visible without checking CloudWatch directly.

mvn clean package builds a shaded fat jar; the Dockerfile builds on amazoncorretto:17 and runs it through the Lambda Runtime Interface Client. cloudformations/cloudformation.yml provisions the image-based Lambda, an execution role scoped to TenantConfigurations/* in S3 plus DynamoDB and VPC/log permissions, a security group, and the 5-minute EventBridge rule, separate stacks for develop and production, both driven by Bitbucket Pipelines variables. A dedicated run-sonar-scan-quality-gw pipeline runs the SonarCloud gate ahead of every build.

Locally, the same container image runs through AWS SAM: sam build compiles inside a container matching the Dockerfile, and sam local invoke (or sam local start-api, which exposes the same handler behind a local POST /crm route) triggers a real run against whichever Authority/Assetic/AWS endpoints are configured in template.yaml: there's no mock layer, so local runs are pointed at sandbox tenants rather than production.

◆ Good to Know

  • Fully scheduled, not event-driven: a single EventBridge rule fires the Lambda every 5 minutes, and each of the 4 stages polls for changes since its own last-run bookmark on S3.
  • Within a stage, individual tasks/Work Requests/Work Orders are processed concurrently across a 100-thread pool, even though the 4 stages themselves run one after another.
  • A Work Request or Work Order can trigger more than one Authority task per poll: each condition (inspector assigned, rejected, in-progress, completed, new note) is checked independently rather than as a single state machine.
  • DynamoDB tracks up to 4 retries per item, with a 3-minute cool-down before a received/failed entry is retried, so an attempt still in flight isn't raced by the next run.
  • Ships as a container-image Lambda, so local testing runs through AWS SAM/Docker against real sandbox Authority and Assetic endpoints; there's no mock/stub layer.
