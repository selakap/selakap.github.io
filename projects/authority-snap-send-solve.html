Case Study

Civica Authority ↔ Snap Send Solve Integration

Two independently deployed services that together form one bidirectional loop between Snap Send Solve (a citizen issue-reporting app) and Civica Authority (council CRM): a scheduled AWS Lambda pulls Authority activity out to Snap Send Solve, and a multi-tenant ECS Fargate API turns new Snap Send Solve reports into fully resolved Authority CRM records, correlated through a shared DynamoDB idempotency table so neither service needs to know the other's internals.

◆ The Problem

Residents report issues, potholes, illegal dumping, damaged signage, through the Snap Send Solve app, but the council's actual workflow, the CRM record, the assigned officer, checklist data, attachments, and the eventual close-out, all lives in Civica Authority. Left disconnected, someone has to manually re-key every new Snap Send Solve report into Authority as a CRM case, resolve who the requestor actually is, work out which property the address belongs to, and then separately remember to update Snap Send Solve every time that CRM case changes so the resident isn't left staring at a report that says "Open" long after the work is done.

Rather than one monolithic integration, this was built as two focused services that each own one direction of the sync and never call each other directly: a multi-tenant CRM API that any tenant's inbound integration can POST a report to, and a scheduled job that owns everything about polling Authority and talking back to Snap Send Solve for one specific tenant.

◆ Two Services, One Loop

The CRM connector (s3_civica_crm_connector_service) is a standing Spring Boot API on ECS Fargate. It has no idea Snap Send Solve exists; it just accepts a generic "report" payload over HTTP, resolves which tenant it belongs to from the request's hostname, and creates the matching Authority CRM record.

The scheduled task (s3_authority_sss_integration, built first for an Australian council) is an AWS Lambda that runs every 5 minutes. It owns the Snap Send Solve side entirely: it pulls new Snap Send Solve reports and forwards them to the CRM connector's public URL, then separately polls Authority for task comments and CRM closures and pushes those back to Snap Send Solve as status updates, messages, or an external-agency triage.

1

Discover New Reports

SSSReportService polls the Snap Send Solve API for reports created since the last run (bookmarked on S3) and POSTs each one, as-is, to the CRM connector's tenant-scoped URL with an x-api-key header.

2

Resolve the Tenant

The CRM connector reads the request's host header (e.g. council-df9dwe45.…), splits it into a tenant name and recipe code, resolves the tenant's numeric code via a central SmartGlue portal API, and loads that tenant's cached config and secrets (60-minute TTL) before validating the caller's x-api-key.

3

Transform & Resolve the Requestor

A tenant-specific JOLT spec reshapes the raw report into an Authority CRM payload. The reporter is matched against Authority's Name Register by email and by the last 9 digits of their phone number; no match falls back to either a configured default NAR id or creating a brand-new name record inline.

4

Create the CRM Record

The connector geocodes the report's address to an Authority parcel, builds the checklist items configured for that tenant and category, creates the CRM record and property link in Authority, then uploads every attachment, downloading it first if the report only supplied a URL.

5

Record the Correlation

A DynamoDB row is written keyed by the new Authority CRM id as target_id and the original Snap Send Solve report id as source_id, partitioned under the CRM connector's own tenant-integration id. This one row is what lets the scheduled task find its way back later.

6

Sync Task Comments Out

Back in the scheduled task, TaskService polls Authority for workflow tasks matching a configured action code, looks up the DynamoDB row to confirm this CRM actually came from the connector, and posts the task's comment to Snap Send Solve as a message to the reporter.

7

Sync Closure & Triage Out

CrmService polls modified Authority CRMs; an in-progress CRM updates the Snap Send Solve report's status, and a closed CRM either closes the report outright or, if Authority recorded a referral to an external agency, looks up that agency's Snap Send Solve authority id from a tenant config mapping and triages the report to them instead.

Neither service ever calls the other's internal APIs. The scheduled task only knows the connector's public, tenant-scoped URL (configured per deployment as S3_CRM_API) behind the same shared Application Load Balancer used across this developer's other Civica integrations; the connector only knows it received a report over HTTP. The only thing that ties a Snap Send Solve report to the Authority CRM it produced is one row in a DynamoDB table both services happen to write to, using each other's ids as opposite keys.

◆ Cross-Service Correlation via DynamoDB

This is the piece that makes two loosely coupled services behave like one coherent integration. When the CRM connector creates an Authority CRM, it writes a row with the CRM id as target_id and the Snap Send Solve report id as source_id. Later, when the scheduled task sees that same CRM show up in its own poll of Authority, it doesn't know or care that a separate service created it, it just queries integrationrecords by target_id: a hit means "this CRM originated from a Snap Send Solve report, and here is that report's id to push the update to."

◆ Multi-Tenant Resolution

The CRM connector is deployed once and serves every tenant on the SmartGlue platform, not just one council. Tenant identity comes entirely from the request, never from a code path:

1. Parse host header{tenant}-{recipe}.domainTenant name + recipe code
2. Resolve tenant codeSmartGlue portal tenant-code APINumeric tenant code
3. Build client key{tenantCode}-{recipeCode}Cache key for config & secrets
4. Load & cache configS3 TenantConfigurations/{clientKey}/config.jsonAuthority creds, JOLT specs, checklist & task mappings (60-min TTL)

The same shared Application Load Balancer routes /crm, /crm/*, and /actuator/* to this one ECS service for every tenant hostname; there is no per-tenant infrastructure to provision, only a new S3 config object and a new hostname on the ALB listener rule.

s3_authority_sss_integration builds a shaded jar and a container image on amazoncorretto, deployed as an image-based Lambda with a cron(0/5 * * * ? *) EventBridge rule, one CloudFormation stack per client under cloudformations/{council}/{uat,prod}.

s3_civica_crm_connector_service deploys as a Fargate task (256 CPU / 512 MB) behind the shared SmartGlue-Integrations ECS cluster and ALB, with a health check on /crm/healthz and a task role scoped to the SmartGlue S3 bucket, DynamoDB, and Athena/Glue (used elsewhere on the platform for report querying). Both repos run a dedicated SonarCloud pipeline on every push.

◆ Good to Know

  • The two services never call each other directly; a shared DynamoDB table, written by one and read by the other via target_id, is the only integration point between them.
  • The CRM connector is genuinely multi-tenant: it was built once for one council's Snap Send Solve traffic but resolves tenant, config, and secrets entirely from the request's hostname, so any tenant's inbound integration can reuse it.
  • Requestor matching reuses this developer's phone-suffix matching technique from other Civica Authority integrations, comparing the last 9 digits rather than a full formatted number.
  • The scheduled task's four stages run sequentially with a fixed pause between each (task, CRM, retry, report) rather than in parallel, while the items inside each stage are still processed concurrently.
  • A NAR lookup path backed by a Parquet data store on S3 exists in the codebase but is fully commented out; the live path queries Authority's Name Register directly instead.
  • Failed DynamoDB entries are retried up to 3 times with a 3-minute cool-down, and the retrier itself decides whether a failure was a task-sync or CRM-sync failure by pattern-matching the stored source_id.
