Case Study

Authority / CM10 Public Forms Integration

An event-driven integration service that takes public form submissions coming out of Drupal and pushes them into Civica Authority (records/CRM) and Content Manager 10 (document management) — keeping attachments and submission state in sync without anyone re-keying a form by hand.

◆ The Problem

Public-facing council forms built in Drupal generate a steady stream of submissions — rates enquiries, animal registrations, waste requests, each with its own attachments — that ultimately need to land as a proper record in Civica Authority and, in some cases, as a document in Content Manager 10. Doing that by hand doesn't scale, and a synchronous call straight from the Drupal site into Authority couples a public, internet-facing form directly to an internal line-of-business system: any slowness or outage on the Authority side becomes an outage for the public form.

This service decouples the two. Drupal only ever talks to a small, disposable ingest endpoint; everything after that — validation, authentication, CRM record creation, attachment upload, document management sync — happens asynchronously, per tenant, with a webhook reporting the result back once it's done.

◆ How It Works

1

Form Submission

A public Drupal form posts its submission — JSON payload plus any attachments — to an API Gateway endpoint, authenticated with a per-tenant x-api-key.

2

Ingest & Persist

A lightweight Python Lambda validates the request and writes the submission payload straight to an S3 bucket, then returns immediately — Drupal never waits on Authority or CM10.

3

Event Trigger

The S3 object-created event fires an EventBridge rule, which launches a one-shot ECS Fargate task running the Spring Boot integration app — no server sits idle waiting for work.

4

Sync to Authority & CM10

The task loads that tenant's config from S3, then checks DynamoDB for an existing record of this submission's source ID — skipping it if already processed successfully, or resuming from wherever a prior attempt left off. It authenticates against Authority and Content Manager 10, creates the CRM record and its attachments in Authority, and pushes documents into CM10 where required, recording progress in DynamoDB at each stage.

5

Completion Webhook

Success or failure is reported back to the source system via a completed-event webhook, so status is visible upstream without anyone checking AWS directly.

The pipeline is fully event-driven and stateless between steps: nothing polls, and no compute runs unless there's an actual submission to process. Tenant identity flows through the whole chain via TENANT_ID, so the same Lambda and the same ECS task image serve every council — only the config and credentials resolved from S3 differ per tenant.

DynamoDB (integrationrecords) is the only durable state in the pipeline: before doing any work, the task looks up the submission's source ID and skips it if it's already succeeded, or resumes from the last completed stage if a previous attempt failed partway through — up to four retries. The S3 submission payload itself is deleted as soon as the CRM record is created in Authority — the task doesn't wait for the CM10 and attachment steps to finish — and the same cleanup runs on any processing failure too, so the ingest bucket never accumulates stale submissions.

Every push through Bitbucket Pipelines runs a SonarCloud quality scan before anything is built, then packages the Spring Boot app and the Python Lambda as Docker images, pushes them to their own ECR repositories, and applies the CloudFormation stacks that own the ECS task definition, IAM roles, the EventBridge S3 trigger, and the Lambda/API Gateway front door — separately for UAT and PROD, driven entirely by pipeline variables rather than anything hardcoded in the templates.

◆ Project Layout

Two deployable components share one repo: the Spring Boot sync app that does the real Authority/CM10 work, and a small Python Lambda that's just an authenticated front door into S3.

repo layout

├─ clients/              # low-level AWS clients (S3)
├─ config/               # Spring config: AWS clients, async executor, env binding
├─ constants/            # shared string / status constants
├─ data/                 # internal request/tracking state (not wire models)
├─ helpers/              # orchestration per concern: Authority, CM, Secrets, S3, HTTP, DynamoDB
├─ managers/             # lower-level API callers used by helpers
├─ models/               # request/response DTOs (Drupal, Authority, CM, secrets)
└─ services/             # top-level services — MainService is the entry flow

python-lambda/app.py     # API Gateway → S3 ingest Lambda
cloudformations/          # ECS task + ECR + Lambda/API Gateway stacks
scripts/                  # deploy scripts invoked by bitbucket-pipelines.yml

The app is deliberately built to run as a one-shot task rather than a long-lived server (WebApplicationType.NONE): it reads BUCKET_NAME and OBJECT_KEY for the submission it was invoked to process, runs the sync, and exits.

◆ Good to Know

  • Multi-tenant by design — the same Lambda and ECS task image serve every council; only TENANT_ID and its S3-backed config differ.
  • The ECS task is intentionally one-shot, not a long-running server, so there's no idle compute cost between submissions.
  • Content Manager 10 sync is optional per submission — not every form needs a document pushed to CM10, only a CRM record in Authority.
  • DynamoDB tracks up to 4 retries per submission, so a transient Authority/CM10 outage doesn't mean the form has to be resubmitted from scratch.
  • UAT and PROD are separate CloudFormation deployments driven by Bitbucket Pipelines variables, with a SonarCloud gate ahead of every build.
