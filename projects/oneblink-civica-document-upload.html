Case Study

OneBlink → Civica Authority Document Upload

An ASP.NET Core service, packaged as a container-image AWS Lambda behind API Gateway, that receives a OneBlink form-submission webhook the moment a field officer taps submit, pulls the completed report PDF and every attachment straight out of OneBlink's own API, and files them into Civica Authority's records management against the right account, all before the officer has driven to the next job.

  • .NET 10
  • ASP.NET Core
  • AWS Lambda
  • Amazon API Gateway
  • OneBlink SDK
  • Civica Authority
  • Docker
  • Bitbucket Pipelines
  • SonarQube
  • xUnit

◆ The Problem

A field officer completes a compliance or inspection form in OneBlink and hits submit, but that submission living inside OneBlink isn't the same as it being on the record: Civica Authority is the council's actual system of truth, and without this integration, getting the finished report and any photos out of OneBlink and filed against the correct Authority account is a manual job, find the submission, download its PDF, download each attachment, work out which account it belongs to, and upload each file by hand into records management.

This is the return half of the round trip: a companion integration on this site already covers Authority dispatching pre-filled OneBlink jobs out to officers; this one covers what happens the moment an officer sends a completed form back.

◆ How It Works

1

Receive the Webhook

OneBlink POSTs a SubmissionEvent (form id, submission id, forms-app id) to /oneblinkcivica/api/submission with an x-api-key header, straight through API Gateway's proxy integration into the ASP.NET Core Lambda.

2

Resolve Tenant & Validate

The request's Host header ({tenantName}-{recipeCode}.…) resolves a tenant code via the platform's Portal API, which also loads that tenant's recipe config from S3 and resolves any secret-manager-backed values. The inbound x-api-key is checked against the tenant's configured OneBlink key before any OneBlink or Authority call is made.

3

Map the Form

The tenant's ONEBLINK_FORMS_CONFIG is a JSON array mapping each OneBlink form id to which field holds the Civica account number and which external document type the upload should be filed under, looked up by this submission's form id.

4

Fetch & Validate the Account

The submission data is fetched via OneBlink's own .NET SDK, the account-number field is extracted, and it's parsed and validated as a Civica formatted account number (AccountType.Year.Number.Version) before anything is uploaded anywhere.

5

Pull the Report & Attachments

The submission PDF is fetched via OneBlink's PDF client; the form's own element definition is walked recursively to find every file-upload field, and each attachment file behind those fields is streamed down from OneBlink individually.

6

Upload & Report

The report PDF, then every attachment, is POSTed to Civica Authority's records-management attachments endpoint against the resolved account, authenticated with a single bearer token cached for the request. The outcome, success or failure, is sent to the platform's completed-event endpoint, tagged with the OneBlink submission id and the Authority account.

Unlike the shared Application Load Balancer this developer's other Civica Authority integrations run behind, this service only ever needs to receive OneBlink's own outbound webhook, not serve council-facing traffic, so it sits behind a dedicated API Gateway with a single Lambda proxy integration instead.

◆ Official SDK vs. Hand-Rolled

This project sits right next to its sibling on this site, the Authority-to-OneBlink job/prefill integration, but the two ecosystems handle OneBlink's developer-key authentication very differently. OneBlink ships official SDKs for JavaScript and .NET only.

This integration (.NET)Sibling integration (Java)
OneBlink clientOfficial OneBlink.SDK package (FormsClient, PdfClient)No SDK available: hand-built HTTP calls
Auth tokenHandled internally by the SDKSigned JWT constructed by hand, mirroring the .NET SDK's own claim shape
Form definition parsingdynamic deserialization via the SDK's own modelsManual JSON walking of Authority's own response shapes

Using the real SDK here means authentication, retry semantics, and response typing are OneBlink's own responsibility rather than this developer's; the trade-off shows up in OneBlinkClientFacade instead, an interface wrapping every SDK call so it can be mocked in tests without a live OneBlink environment, since the SDK's own client classes aren't designed to be swapped out for a test double.

◆ Attachment Discovery

OneBlink forms are trees, pages contain sections, sections contain elements, and a file-upload field can be nested arbitrarily deep. Rather than requiring every tenant to hand-list which fields hold attachments, OneBlinkService walks the form's own element definition recursively, capped at five levels deep, collecting the name of every element whose type is "files":

app/Services/OneBlinkService.cs 
void CollectFileFieldNames(dynamic elements, List<string> fieldNames, int depth)
{
    if (depth > 5) return;

    foreach (var element in elements)
    {
        if (element.type == "files")
            fieldNames.Add(element.name);

        if (element.elements != null && element.elements.Count > 0)
            CollectFileFieldNames(element.elements, fieldNames, depth + 1);
    }
}

Those field names are then looked up against the actual submission data to pull out every attachment's id and filename, so adding a new photo-upload field to an existing form is picked up automatically on the next submission, no config change required on this side at all.

◆ Form → Account Mapping

Every tenant's ONEBLINK_FORMS_CONFIG is a small JSON array, one entry per OneBlink form this integration should handle:

ONEBLINK_FORMS_CONFIG (per tenant) 
[
  {
    "FormId": 1234,
    "UNIDFieldName": "unid_fa",
    "AttachmentType": "ATTACH_CC"
  }
]

UNIDFieldName names the form field whose value is the Civica formatted account number for this submission; AttachmentType is the external document type code every upload for that form is filed under. The account number itself is validated by shape, exactly three dots, four parts, AccountType.Year.Number.Version, before any upload is attempted, so a misconfigured form field fails fast with a clear message instead of a confusing upstream Authority error.

◆ Sequence: A Submission Becomes a Filed Document

The highlighted band marks the Lambda's active lifetime for this request; the bearer token is fetched once and reused for the report upload and every attachment upload within the same request.

deploy-OneBlinkCivica-dev and deploy-OneBlinkCivica-prod are both manually triggered from Bitbucket Pipelines rather than running on every push; each runs the xUnit suite first, then uses AWS SAM to build the Docker image, push it to ECR, and update the Lambda stack via CloudFormation. The Lambda itself runs inside a VPC with an execution role scoped only to s3:GetObject on the tenant config prefix.

Code quality runs differently to this developer's Java integrations: instead of a SonarCloud-integrated CI step, the README documents a locally-run SonarQube container plus the .NET-specific dotnet-sonarscanner tool, which, unlike the Java Maven plugin, doesn't understand sonar-project.properties at all and takes every setting as a command-line parameter instead.

◆ Good to Know

  • Uses OneBlink's official .NET SDK directly, a genuine contrast to the sibling Authority-to-OneBlink integration on this site, which had to hand-build a signed JWT since no Java SDK exists for OneBlink's developer-key auth.
  • Attachment fields are discovered by recursing through the form's own element definition (capped at 5 levels), not configured by hand, so a new file-upload field on an existing form is picked up automatically on the next submission.
  • The Civica account number is validated by shape before any upload is attempted, exactly three dots, four parts, so a misconfigured form field fails fast with a clear error rather than surfacing as a confusing Authority-side failure.
  • Runs behind a dedicated API Gateway proxy integration rather than the shared ALB used by this developer's other Civica Authority integrations, since it only ever needs to receive OneBlink's own webhook, not serve council-facing traffic.
  • Code quality uses a locally-run SonarQube instance and the .NET-specific SonarScanner, a different toolchain from the SonarCloud-integrated pipelines used on this developer's Java/Maven integrations.
  • Both deployment pipelines (dev and prod) are manually triggered from Bitbucket Pipelines rather than running automatically on push.
