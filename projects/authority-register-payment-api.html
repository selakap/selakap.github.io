Case Study

Civica Authority Register Payment Lookup API

A multi-tenant Python service, packaged as a container-image AWS Lambda behind FastAPI and Mangum, that resolves everything owed against an Authority payment register in one call: it walks a chain of related Civica Authority records concurrently, normalises the result through a per-tenant JOLT spec, and returns it as a clean, ready-to-bill list, built as reusable platform scaffolding for whichever downstream payment system a council needs it to feed.

◆ The Problem

A single Civica Authority "register" record, a compliance or licensing account tied to a property, can carry a whole chain of related data spread across several separate Authority endpoints: the pending payment requests against it, the register's own extended details and linked parcel, and the applicant on file who's actually meant to be billed. None of that is exposed as one Authority endpoint, so answering "what does this register currently owe, and who do we bill?" means several sequential lookups per payment request, then reshaping whatever comes back into whatever format the council's actual payment or receipting system expects, which differs tenant to tenant.

This service exists to do that joining and reshaping once, behind a single endpoint, so a downstream payment integration never has to know Authority's data model at all, only the tenant-specific, JOLT-mapped shape this API hands back.

◆ How It Works

1

Resolve the Tenant

AppHelper parses the inbound Host header as {tenantName}-{recipeCode}.…, resolves tenantName to a numeric tenant code via a portal lookup API, and loads that tenant's config and secrets from S3 (cached 60 minutes per clientKey), then validates the caller's x-api-key unless that tenant has opted out.

2

Fetch Pending Payment Requests

For the requested register number, AuthorityHelper.get_payment_requests pages through Authority's payment-request collection (100 at a time via $skip) to collect every request with no receipt raised yet.

3

Walk the Chain, Concurrently

Each payment request needs its own register, that register's extended details and linked parcel, and its applicant's name, four to five further Authority calls per row. RegisterPaymentSourceCollector runs that chain for every payment request at once, bounded by a semaphore, rather than one row at a time.

4

Transform Per Tenant

Each collected row is run through that tenant's own payment_jolt_spec.json (a separate cached S3 object) via the stateless JoltHelper, producing one RegisterPaymentDetails per row; a row the spec can't map is logged and skipped rather than failing the whole response.

5

Respond & Report

The transformed list is returned as the response body, and an "integration completed" event, tagged with tenant/recipe codes, is POSTed to a central webhook on both success and failure so the run is visible without checking Lambda logs directly.

◆ Concurrent Data Collection

The chain behind one payment request, register → extended register & parcel, register → applicants → name, is inherently sequential on its own, but different payment requests don't depend on each other at all. Running that chain one row at a time against a register with around 100 pending payment requests measured roughly 3 minutes 40 seconds end to end in testing, far too slow for a synchronous API response.

app/services/register_payment_source_collector.py 
DEFAULT_CONCURRENCY = 10

async def collect(self, int_data, payment_requests):
    return list(await asyncio.gather(
        *(self._build_one(int_data, pr) for pr in payment_requests)
    ))

async def _build_one(self, int_data, payment_request):
    async with self._semaphore:
        # register -> extended register -> parcel
        # register -> applicants -> name
        ...

Since this app is single-threaded asyncio rather than a thread pool, the Semaphore caps how many rows are in flight at once, not how many OS threads run; httpx.AsyncClient's own connection pool already handles the concurrent requests underneath. asyncio.gather preserves input order regardless of which row's chain actually finishes first, so the response list still lines up with the original payment-request order. DEFAULT_CONCURRENCY is a single constant, the tuning knob for trading wall-clock time against load placed on Authority's API.

◆ Multi-Tenant Resolution

One deployed Lambda, one image, serves every tenant on this hostname pattern; nothing tenant-specific is baked into the code or the container.

◆ Observability & Error Handling

Every request gets one correlation id threaded through the whole call, and every failure mode maps to a specific, structured JSON shape rather than a bare traceback.

FailureStatusHandled by
Malformed/missing Host header400BadRequestError → global AppError handler
Missing/invalid x-api-key401UnauthorizedError → global AppError handler
Authority (or any upstream) non-2xx / timeout502HttpCallError → dedicated handler, upstream body kept out of the client response
Anything unexpected500Generic Exception handler, full traceback logged server-side only

On Lambda, an ASGI middleware pulls the AWS request id straight off Mangum's Lambda context and uses it as the request's track_id, so a log line in CloudWatch and the trackId field in an error response always point at the same request; a plain ASGI wrapper is used deliberately instead of Starlette's BaseHTTPMiddleware, whose task-group-based call_next() would otherwise double-log an already-handled exception. The same middleware echoes track_id back as an x-track-id response header. Deeper down, HttpHelper masks access_token/authentication_token fields with regex before logging any response body, so a debug-level log line never leaks a live Authority token.

pytest.ini runs with coverage on every invocation (--cov=app) and fails the build outright if total coverage drops below 90%, both locally and in CI, ahead of the SonarCloud quality gate. The Lambda ships as a container image built from public.ecr.aws/lambda/python:3.13, wired to an existing shared ALB via a target-group/listener-rule pair rather than API Gateway, consistent with this developer's other Civica Authority integrations. lifespan="off" is set on Mangum deliberately: the shared httpx.AsyncClient is a module-level singleton created once at cold start so warm invocations reuse its connection pool, and running a full ASGI lifespan on every invocation would tear that client down and immediately break the next warm call.

◆ Good to Know

  • The Authority-side data collection, tenant resolution, config/secrets caching, token handling, and error handling are fully built and tested; the outbound "Source" leg (the actual payment/receipting vendor a council needs this pushed to) is an intentionally empty stub, so today the JOLT-transformed result comes back as the API response itself rather than being forwarded on.
  • This is the first project on this portfolio built on Python/FastAPI/asyncio rather than Java/Spring Boot; the tenant-resolution, config-caching, and OAuth2 token-caching patterns are deliberately ported from this developer's Java Civica Authority integrations rather than reinvented.
  • Concurrency is capped by an asyncio.Semaphore, not a thread pool; this app is single-threaded asyncio throughout, and httpx.AsyncClient's own connection pool handles the concurrent HTTP calls.
  • A missing or broken per-tenant JOLT spec doesn't fail config loading, it just leaves payment_jolt_spec unset, which the transform step then reports as a 404-style NotFoundError rather than a 500.
  • The CI pipeline fails the build if test coverage drops below 90%, enforced by pytest.ini's --cov-fail-under=90 before SonarCloud's own quality gate even runs.
